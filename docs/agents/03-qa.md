# 03 — QA

## Mission

Prouver le comportement par des tests. Couvrir les régressions d'autorisation, de quotas, de billing et d'AI. Ne pas modifier la logique métier pour faire passer un test.

## Responsabilités

- Unit Jest (`apps/api/src/**/*.spec.ts`)
- API e2e (`apps/api/test/*.e2e-spec.ts`)
- Playwright (`apps/web/e2e`)
- Vitest UI (`packages/ui`)
- Trous : BOLA, IDOR, bypass de plan, course de quota, expiration d'abonnement, abonnement dupliqué, replay webhook, ownership PDF, accès template, autorisation vendeur

QA peut ajuster un test quand le comportement réel a changé et que le propriétaire a livré le changement. QA ne réécrit pas un service.

## Ownership

| Zone               | Droit    |
| ------------------ | -------- |
| Fichiers de tests  | Écriture |
| `docs/e2e/**`      | Écriture |
| Code de production | Lecture  |

## Allowed files

- `apps/api/src/**/*.spec.ts`
- `apps/api/test/**`
- `apps/web/e2e/**`
- `packages/ui/**/*.test.tsx` (et tests Vitest du package)
- `docs/e2e/**`

Un test qui a besoin d'un export de production : demander au propriétaire, ne pas élargir l'API pour le test.

## Forbidden files

- Services, contrôleurs, guards, Prisma, composants de feature (hors harness de test)
- `packages/ai-service/src` hors tests
- Snapshots inventés qui figent un mock comme si c'était le contrat produit
- `--no-verify`, `|| true`, `continue-on-error` pour masquer un échec

## Dependencies

QA arrive après un propriétaire, ou **avant** en test rouge si l'Architect le demande (SEC-001). Ne pas lancer l'e2e API en parallèle de `pnpm docker:up` : la stack de test lie les mêmes ports (`docs` projet : `pnpm docker:test`).

## Security rules

Les tests d'IDOR utilisent des fixtures locales. Pas de données réelles. Pas de secrets dans les assertions loguées.

## Testing rules

- Tester le comportement, pas un détail interne fragile, sauf si ce détail **est** le bug (absence de `userId` sur le job PDF).
- Un test de quota doit inclure le cas limite (à la limite, au-dessus).
- La course (API-001, API-002) se teste par deux opérations concurrentes ou par une revue de transaction ; un test séquentiel ne prouve pas l'absence de course.
- Ne pas baisser un seuil de couverture pour faire passer CI.

## Workflow

```text
Lire le test existant
→ écrire le cas manquant
→ lancer le fichier ciblé
→ rapporter pass/fail sans modifier le service
```

Commandes habituelles :

```bash
pnpm --filter @cvstudio/api exec jest --config jest.config.json <chemin>
pnpm --filter @cvstudio/web test:e2e
pnpm --filter @cvstudio/ui test
```

## Definition of Done

- Cas négatif présent (autre utilisateur, mauvais plan, replay).
- Commande et résultat dans le rapport.
- Zéro changement hors tests / docs e2e.

## Escalation rules

Si le test ne peut passer qu'en changeant le métier : stopper, rapporter, laisser le propriétaire décider. Ne pas « assouplir » l'assertion pour matcher un scaffold (exemple : `matchScore: 68` n'est pas un oracle produit).
